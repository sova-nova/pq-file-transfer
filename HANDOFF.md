# Handoff: PQ File Transfer → PQ Suite v3

For starting a fresh conversation (with Claude or anyone else) without losing the thread. Read this first, then the design document.

- **Design document:** https://claude.ai/code/artifact/9bfa4d70-d640-4282-a63d-a10e3ac96310

## What exists (version 0.7.0)

## How it fits together

- **One server, two protocols.** `pq-server` decides by a connection's first message: `RELAY_HELLO` means v3 (mailboxes), anything else is v2 file transfer. State for v3 lives in `<storage>/v3` (database and the relay's signing key).
- **Relay trust.** Clients pin the relay ID (SHA-256 of its public key) from the invite; the relay proves it every connection by signing the client's nonce.
- **Mailboxes.** Created with a single-use invite (made on the relay with `--create-invite`). The mailbox has its own random ID and its own ML-DSA key, separate from the identity key. Senders deposit with a send token; the owner signs in and collects.
- **Messages.** A signed record (sender, conversation, recipients hash, time, `own_prev`, `seen`) is sealed in an envelope encrypted to the recipient's long-term ML-KEM key, padded to 4/16/64 KiB. The relay sees only mailbox ID, token hash and the sealed bytes.
- **Local secrets.** History and the mailbox access key are protected by keys derived from the identity's private KEM key (`KeyStore::derive_local_key`), so there is no separate secret file and a passphrase change doesn't affect them.
- **Threading.** `MessagingEngine::pump()` is called from ONE worker thread; every other method is safe from the UI thread. `ChatWidget` owns both, and `MainWindow` deletes it before the key store (the worker uses the keys).

## How verification works (important)

The assistant's sandbox has **no Qt, no CMake, no real liboqs and no SQLite header**. So:

- Code is compiled with `-Wall -Wextra -Wpedantic -Werror` against a fake liboqs and a small SQLite header shim, and the full suites run against those.
- The Qt code (`chat_widget`, `main_window`) is only type-checked against a hand-written stub of the Qt classes. That catches typos and API mismatches in our own code, not Qt misuse.
- **The first CI run is the real test** for the GUI, CMake, Windows and the real liboqs. If it fails, paste the compiler error.
- Test totals at last run: **1,846 checks, 0 failed** (sharing 117, keys 69, contacts 58, chat_formats 280, history 233, relay_protocol 172, relay_store 165, e2e 48, relay 228, chat 88, relay_setup 30, group 358). The group suite takes about twelve minutes. If a run is interrupted, check for a stray `pq-server` process (`pkill -x pq-server`) before the next: it can hold a port and make an unrelated suite fail once. The group suite takes about nine minutes. Run the suites one at a time: they pick ports from a shared range, and two at once can collide. The group suite runs up to 18 real engines and takes a few minutes. The relay limits mailbox registrations to 10 per minute per address (hard-coded, separate from `--rate-limit`), so tests with many people wait out that window. Linux and macOS only for the process-spawning ones. `ctest --test-dir build --output-on-failure`.

## Operational facts and gotchas

- **Relay and clients must be updated together** when the v3 wire format changes (it did in M2: envelopes now carry a token hash). The relay database migrates itself from schema 1 to 2; back up `<storage>/v3` before upgrading.
- **Back up `<storage>/v3`** on the relay. Losing `relay_private.key` makes every client report "relay changed".
- **An invite does nothing if the relay isn't running.** (A real mix-up that happened; the error message now says so.)
- **Run `--create-invite` as the same user the service runs as.** Otherwise `<storage>/v3` ends up owned by the wrong user and the service can't open it. (The program now detects this at startup and explains how to fix it.)
- **Always use one absolute `--storage` for the server and for `--create-invite`.** A second folder means a second relay identity, and the client reports "relay's identity does not match the one you pinned" (a real mix-up that happened). `--create-invite` now refuses when the storage has no identity (override: `--allow-new-identity`), prints `Relay state:` with the folder it used, and the server warns when it falls back to the temporary default.
- **`--bind` must include an address the client can reach.** A relay bound to the WireGuard address refuses LAN connections.
- **Revoking a card is not enough** to cut someone off: a first message carries a token grant that replaces the card's token on the receiver's side. Use **Revoke access** (`revoke_tokens_for`).
- **All clients must be updated together (new wire formats).** Messages are now written as record version 2 inside envelope inner version 2. A client from before this change can't read them: it drops them silently, and the relay deletes them once the old client acknowledges. New clients still read everything the old ones wrote. The relay itself is unaffected (it never parses records), but update every client before relying on messages between them.
- **Update every client together again, and the relay if you want the larger token limit.** Group members now exchange send tokens through the creator in a new record type (Forward, type 5). A client from before this change drops it, so groups work between updated clients only. The relay's default per-mailbox token limit went from 256 to 1024 (a 16-person group uses 15 per member); the relay needs rebuilding for that, and clients don't care.
- **`history.db` is upgraded automatically** to schema version 5 the first time the new app opens it. From version 1 it must rewrite a table, so it first copies the old file to `history.db.before-v2` next to it (kept, never overwritten); from version 2, 3 or 4 it only adds tables and needs no copy. A history made by a *newer* app is refused with an explanation rather than opened. Once the upgrade has been confirmed good, the `.before-v2` copy can be deleted.
- **Clients keep history only on the device** until M4. Back up `~/.pq-file-transfer/` including `history.db`.
- The deployment is a Proxmox VM running the relay with WireGuard. The relay is currently reached at `10.0.0.248:9000` on the LAN; the WireGuard clients use the `10.8.0.x` range. Check the real service unit name and `--bind` before assuming anything.

## M5: attachments (built and tested; all 5 steps done)

An attachment is a chat message that points at an encrypted file parked on the sender's relay. Each recipient has their own one-time download token; the relay deletes the file when every token is redeemed, when the sender withdraws it, or when it expires. The existing transfer-ID file transfer (the v2 protocol in `server/main.cpp`, the "Send File" tab) is left alone and keeps working.

Decisions, settled with the maintainer:

| # | Decision |
|---|---|
| 1 | The old transfer-ID tab stays; attachments are added next to it. |
| 2 | The file lives on the **sender's relay**, named in the message with its pinned identity (as for archives); recipients on other relays connect to it. |
| 3 | Groups: one file, one token per member (up to 16). |
| 4 | Limits: **1 GiB per file, 4 GiB stored per mailbox, expiry 7 days by default, 30 at most**; all relay settings (`--max-attachment-mib`, `--attachment-quota-mib`, `--attachment-max-days`). |
| 5 | Each file has its own random key, so a chunk number can safely be the nonce (unlike M4's archive entries, where two members can race for the same number under one shared key). |
| 6 | A download can restart from a given chunk. |
| 7 | Never downloaded automatically: the recipient clicks Download and sees the size first. |
| 8 | The sender can see how many recipients have fetched it (the relay already knows). |
| 9 | The relay learns that a mailbox uploaded a file of a given size for N tokens (it must know the uploader, to enforce quotas and let only them withdraw). |
| 10 | File names are sanitised on save, never overwrite anything, and are never opened automatically. |

Per the design: the shared message record (and so the archive) carries only public details (file ID, name, size, chunking, the file's SHA-256, the expiry, the relay); the file key and each recipient's token travel only in that recipient's own envelope, so restoring a chat from its archive can never produce a readable file. Files are not archived.

Build order: 1. relay file store (**done**); 2. client file core: chunk encryption, streaming, hash check, attachment record, per-recipient grants in the envelope (**done**); 3. engine: send and receive for one-to-one chats and groups, the states, download (**done**); 4. GUI (**done**, type-checked only); 5. end-to-end and hostile tests.

**Step 5 as built** (audit; a lighter pass than M4's, at the maintainer's request): the hostile cases were checked against the tests, and the gaps worth closing were closed.

- **A sender who names another relay.** The attachment record carries the relay address, and the app used to connect to whatever it said when the recipient chose Download, so a member could make a recipient's app contact a server of theirs, or an address on the recipient's own network. `note_incoming_attachment` now accepts a file only if the relay named (address and pinned ID) is the **sender's own**, as their identity bundle says; otherwise it is shown but marked not fetchable, with the reason, and the app never connects. Tested: a member's record naming `127.0.0.1:1` is shown as unavailable and the download is refused.
- **Attachments in archives and restores.** `restore_records` and archive catch-up used to skip attachment records, so a restored (or caught-up) chat silently lost them, contradicting what these notes said. They are now carried, and shown as unavailable (the key is never in an archive); one of the user's own, read back, is recorded as outgoing and "no longer on the relay". Tested: a wiped and restored member sees a file she had downloaded, with its name, size and caption, marked not fetchable.
- **A race this audit introduced, found by the full suite, and fixed.** Once archive catch-up carried attachments, a direct chat's archive sync could deliver the record **before** the envelope that holds its key. That created the attachment with no key (unavailable); the envelope then arrived as a duplicate message and was dropped before its key was recorded, so the file stayed unavailable for good. Now an envelope's grant **upgrades** an attachment that arrived first without one (`HistoryStore::grant_attachment`, which only ever fills in a missing key, never replaces one, and never touches a file we sent), even when the message itself is a duplicate. It only showed in the full run, not when the attachment section ran alone, because it depends on the archive having been made first.
- **"Not ready yet", not "can't be fetched".** The record reaches a recipient (by archive catch-up) as soon as it is sent, but the key travels with the envelope, which is sent only once the upload has finished. For that window an attachment with no key was shown as unavailable, which is wrong for a file that is simply on its way. A recent one (record sent within the hour) is now marked **"Waiting for the sender's upload to finish"**, a download attempt says so, and the key's arrival makes it available. An old one with no key (a restored chat) stays unavailable. This is what the full suite's last two failing checks were: the test tried to download the instant the attachment appeared.
- **A relay serving the wrong bytes.** Tested end to end: another file's bytes for the one asked for (refused), only half of the file (nothing saved, failure reported), and the right bytes back (the same download completes, exact). Together with the earlier flipped-bit test, the app saves nothing it can't prove is the sender's file.
- **A non-member sending an attachment into a group** is ignored (tested).
- **Already covered, not repeated:** chunks can't be moved between places or files, and the final fingerprint check (unit tests, with a mutation check); the token is used up only after the file is saved (by construction); wrong, reused and cross-file tokens, expiry, quotas, withdrawal by the owner only, interrupted uploads and restart persistence (relay tests, with a mutation check).
- **Not done, by choice:** no mutation check on the engine this time, and no end-to-end test where the sender lies about the file's fingerprint (it needs a crafted upload; the decryptor's refusal is unit-tested). The 7-day-style expiry of a real attachment can't be tested without moving the clock.

**Working on attachments quickly:** `PQ_ONLY_ATTACH=1 ./test_group ./pq-server` skips sections 1 to 18 of the group suite and runs only section 19 (about three minutes instead of fourteen). Run the whole suite before trusting a change, as the race above shows.

**M5 known limits, in one place:** a file is on the sender's relay, so the sender's relay must be reachable for the recipient to fetch it; attachments held with a not-yet-accepted group invitation, and attachments in a restored chat, are unavailable; one transfer runs at a time; no cancelling a download in progress; the GUI has only been type-checked against a Qt stub.

**Step 4 as built** (`ChatWidget`, plus `MessagingEngine::attachment(file_id)`): the GUI for attachments. It is only type-checked against a Qt stub here, not run.

- **Attach…** beside Send (enabled when a chat is open): a file chooser, then a prompt for how many days the relay should keep it (1 to 30, default 7); what is typed in the message box becomes the caption; a wait cursor shows while a very large file is measured. Errors from the engine (not a file, too large, caption invalid) are shown as they are.
- **The attachment line** in both chat views: `[file] name (size)  -  state`, with the caption underneath: waiting to upload / uploading N%; for the sender, "N of M have it, until <date>" then "everyone has it"; for a recipient, "click to download, until <date>" (with a note about the last failed try if any), downloading N%, "saved to <path>"; expired, withdrawn ("you withdrew it" or "the sender took it back"), "could not be sent: <why>", or "can't be downloaded: it reached you without the key it needs" (after a restore). While a transfer is moving, a 700 ms timer redraws the list and keeps the scroll position, so progress shows without the view jumping.
- **Clicking an attachment** opens its options: **Download…** (an incoming one that is available: the dialog says the file is kept encrypted on the sender's relay and will be saved under a name that can't replace anything and never opened; the next step shows the file's name and size in the folder chooser, defaulting to the Downloads folder), **Copy the file's location** (once saved), **Withdraw it** (for the sender, with a confirmation), or Close. Nothing is fetched or opened without being asked. Clicking an attachment no longer shows the per-member delivery details a group message has.
- **Not done:** the GUI has not been run; there is no way to cancel a download in progress; an attachment's per-member delivery details are not shown; the transfer limits are the relay's and are only reported when an upload is refused.

**Step 3 as built** (`MessagingEngine`, history schema 9): attachments work between people, with no GUI yet.

- **Sending** (`send_attachment`, `send_group_attachment`): the file is fingerprinted (read once, on the calling thread, so a very large file makes the call take a moment), a message record is made and stored at once, and an upload job is queued. **No envelope goes to anyone until the file is on the relay**; then each recipient gets their own envelope (a queued item of the new kind `OUTBOX_KIND_ATTACHMENT`: the record plus that recipient's file ID, key and token) through the ordinary outbox, so delivery, retries and per-member status work as for any message. A relay that is down just means waiting and retrying (the maintainer's choice): the message shows as uploading and nothing is lost. Permanent failures (the file changed after it was attached, it was too large or over quota for the relay, its time ran out while uploading) mark it failed and tell the user. If an earlier upload completed but its confirmation was lost, the relay says "already exists" and a status check lets the retry finish normally. If the user withdraws while it uploads, the upload job takes it down again. The record is archived like any message; the key and tokens are not part of it.
- **Receiving:** an attachment record is validated, stored like a text message (so it has a place in the transcript, and delivery receipts), and `note_incoming_attachment` keeps the file key and our own token (sealed) from the grants in the same envelope (`envelope_grants_`). One that arrives *without* a grant (read back from an archive, or held with a pending group invitation, which keeps records but not grants) is stored as **unavailable**: it shows, but can't be fetched. A restored chat therefore shows its attachments as unavailable, as designed.
- **Downloading** (`download_attachment`, only when the user asks; never automatic): runs on the transfer thread; resumes from whole chunks an earlier attempt left; every chunk is opened and size-checked against the record; the finished file is checked against the signed fingerprint and saved under a safe, unused name; **only then** is the token redeemed. A damaged chunk or a mismatching file is thrown away and the attachment goes back to available with a note (the token is untouched, so it can be retried). "Expired", "already downloaded" and "no such file" (withdrawn before its time, or gone) set the matching state and remove the partial file; a relay that can't be reached leaves the partial file for resuming. `attachment_progress` gives bytes done and in all.
- **States** (`HistoryStore::AttachmentState`): uploading, available, transferred (fetched by us; or, for the sender, by everyone), expired, withdrawn, unavailable, failed, downloading. Expiry is checked locally when shown and by `check_attachments` (every `archive_sync_seconds`), which also asks the relay how many recipients have fetched a file the user sent (`file_status`) so the sender can see "2 of 3 have it"; a file gone from the relay before its time, not withdrawn by us, counts as fetched by all.
- **Withdrawing** (`withdraw_attachment`, sender only): the relay deletes it; recipients who try learn it is withdrawn.
- **Threading:** one background transfer thread for uploads and downloads, started on first use and stopped (interrupting any transfer) in the destructor, so a big file never holds up messages. One transfer runs at a time, so a long upload delays a download.
- **Other changes:** `ChatMessage` / `GroupMessage` have `is_attachment` and an `AttachmentView` (name, size, caption, state, expiry, who has it, where it was saved, a note); `Options::max_attachment_bytes` (1 GiB). A latent oversight was fixed: the deletion-check timer was never started in the constructor, so it ran at once on startup instead of one interval later.
- **Verified end to end** (real relay, real engines): a 3 MiB photo with a caption (over 64 chunks) from one person to another: it shows as an attachment, is not fetched until chosen, is saved byte for byte, the relay's copy is deleted as soon as the only recipient has it, and the sender sees "1 of 1"; the relay's copy does not contain the file's content; a name with a colon and a question mark is made safe by the sender; a second file with the same name is saved as "(2)" and the first is untouched; a group file with one upload and two recipients (the relay keeps it until both have it; the sender sees "1 of 2" then done); withdrawal (the relay's copy is gone, the recipient finds out, only the sender can withdraw, no partial file is left); **a relay that changes one bit of a stored file** (the recipient's app refuses it and saves nothing, the token is not used up, and the same download succeeds once the relay serves it properly); **a relay that is down when the file is sent** (accepted and queued, shown as uploading, goes through by itself when the relay returns, then downloads intact); and limits (a missing file, a keep-time of 0 or 31 days, an over-long caption).
- **Not done:** no GUI (step 4); no mutation check on this step; attachments held with a not-yet-accepted group invitation are unavailable; restoring a chat shows its attachments as unavailable.

**Step 2 as built** (`client/attachment.{h,cpp}`, `message_record`, `envelope`): the client's half, with no engine or GUI use yet.

- **Chunks** (`attachment::seal_chunk` / `open_chunk`): AES-256-GCM under the file's own random key, 48 KiB of plaintext per chunk (49,168 sealed, one relay message each). The nonce is the chunk number (safe here because no two chunks of any file share a key and nonce; unlike M4's archive entries). The file ID, chunk number and chunk count are also bound in as associated data, so a chunk can't be moved, repeated or passed off as part of another file. (The chunk number in the associated data is redundant with the nonce; it is kept as defence in depth, and a mutation check confirmed the nonce alone already refuses a moved chunk.) An empty file is one chunk holding only its tag. `plan_for` makes chunking the relay's protocol accepts for every size up to the 15 GiB limit (tested).
- **Streaming:** `fingerprint_file` (size and SHA-256 in one read), `Encryptor` (reads and seals any chunk on request, noticing a file that changed size while being sent; it recovers from a failed read), `Decryptor` (accepts chunks in order, opens each, writes a temporary file next to the destination, hashes as it goes; at the end checks the size and the SHA-256 the sender signed, and only then saves under a safe, unused name; any mismatch deletes the partial file and saves nothing). Nothing holds a whole file in memory.
- **Resuming:** `Decryptor::begin(resume=true)` keeps whole chunks from an interrupted attempt, drops a partial chunk, **re-hashes what it kept**, and says which chunk to ask for next (`next_chunk()`); a leftover partial file that was tampered with on disk is therefore caught by the final check. Pair it with the relay's start-from-chunk download.
- **Names:** `sanitize_filename` makes a name chosen by someone else safe: valid UTF-8 only; control characters, path separators, characters Windows forbids and text-direction tricks replaced; no leading or trailing dots or spaces; Windows device names defused; at most 200 bytes, cut on a character boundary keeping the extension; never empty. `unique_path` never overwrites anything (a name taken by anything, including a dangling link, gets \"(2)\", \"(3)\"...). Known gap: the check for a free name and the rename are not atomic, so a file created in between could be overwritten on POSIX; acceptable for a save into the user's own folder, but worth knowing.
- **The record** (`RecordType::Attachment`, 10, version 2, part of the transcript like text): file ID, name, size, SHA-256, expiry, the relay's address and pinned ID, and an optional caption; strictly validated (names and captions through the same label check as group titles). It holds **no key and no token**.
- **The envelope** (inner version 3): `Inner::grants`, up to 4 per envelope, each the file ID, the file key and that recipient's own download token. Written as version 3 only when there are grants; an envelope without any is exactly what it was (version 2), and versions 1 and 2 still read. Strictly validated (sizes, no duplicates, version 3 means at least one).
- **Engine:** an attachment record that arrives is explicitly ignored for now; nothing can create one yet (step 3).
- **Verified:** 76 new checks: relay-compatible chunking for every size, chunk tamper-evidence and place binding, 2,000 identical chunks all sealing differently, round trips of empty, one-byte, exact-multiple and 5 MiB files, every way the final check can fail, resuming (including a tampered leftover), safe names, the record and envelope formats with hostile inputs. Five protections were broken in turn; four were caught by the right checks and the fifth (above) is redundant by design.

**Step 1 as built** (`RelayStore`, `RelayService`, `RelayClient`; protocol in `relay_protocol.h`, messages 0x60 to 0x6D, relay schema 7):

- **Upload** (mailbox sign-in): `FILE_UPLOAD_BEGIN` names the file ID, the ciphertext size, chunk size and count (they must fit together; chunks are at least 4 KiB unless the file is one chunk, and at most 64 KiB so each fits one relay message), the expiry, and one token *hash* per recipient (1 to 16, all different). Chunks stream to a temporary file; the relay confirms every 64 chunks and after the last. Only the last chunk makes the file fetchable (the temporary file is renamed). An out-of-order or wrong-size chunk, or a dropped connection, throws the upload away entirely (disk and record), freeing the quota.
- **Download** (no mailbox): `FILE_DOWNLOAD` with the file ID, the token and a start chunk; the relay streams `FILE_INFO`, then each chunk, then an end marker. It does **not** use the token up. `FILE_REDEEM`, sent after the recipient has decrypted and checked the file, does; when the last token is used the relay deletes the file. "No such file" and "wrong token" give the same answer, so file IDs can't be probed. Downloads are rate-limited per address.
- **Withdraw and status** (the owner only): `FILE_CANCEL` removes the file; `FILE_STATUS` says whether it is ready and how many of how many tokens are used.
- **Limits and cleanup:** size per file, stored bytes per mailbox (counting uploads in progress), and how far ahead an expiry may be, all checked on upload begin. The sweeper deletes expired files and uploads unfinished after an hour, and removes any bytes on disk with no record (for example after the operator removes a mailbox), so nothing is orphaned. Files are written under `<storage>/v3/files/`.
- **Verified:** wire format tests with hostile inputs; store tests (quotas, token states, expiry and abandoned sweeps, restart, a version 6 database upgrading); and relay tests over the real protocol, including a file of 70 chunks (past the confirmation window), resuming from chunk 40, a token not being used up by fetching, withdrawal by the owner only, the size and quota limits, expiry bounds, an upload that dies half way, out-of-order and wrong-size chunks, restart, and the bytes of a removed mailbox being swept. Five protections were broken in turn and each made its own check fail.
- **Not yet:** nothing in the app uses this; per-recipient download status for the sender needs the engine; resuming an interrupted *upload* is not supported (it starts again).

## M4: decisions and build order

Archive design: see the design document, "Saved chats: transcript and archive" and "Deleting Saved chats". Settled with the maintainer, in addition to the design:

| # | Decision |
|---|---|
| 1 | The archive lives on the **creator's relay**, named in the grant with its pinned identity; members on other relays connect to it. |
| 2 | 1:1 chats: the person with the **smaller fingerprint** creates the archive, when they next send after upgrading. |
| 3 | **No backfill** of history from before M4 in v1; the app says older history is device-only. |
| 4 | An archive session is authenticated by the existing **challenge signing, one chat per connection** (restoring 100 chats is 100 short connections). |
| 5 | A checkpoint is a **record in the chain**, signed by the member's identity key, outside the displayed transcript (like receipts). Cadence as designed: every 50 messages or each day of activity. |
| 6 | The **keyring** holds per-chat keys and archive keys plus the small history tables that can't be rebuilt from archives (verified people, member tokens, introduced members, issued-token labels, receipt settings). Messages come back from archives. |
| 7 | Registration closes when everyone has joined or after **30 days**; deletion then needs every *registered* key, so a member who never joins can't block it forever. |
| 8 | Only mailbox owners may create archives (keeps the vouching model); the relay **does not record which mailbox** created one, so it still can't link a chat to its members. A per-mailbox rate limit (in memory) and a relay-wide cap bound abuse. |

Build order:

1. Relay: archive storage and operations (create, join, sign in, append with compare-and-swap, fetch), limits, tests. **Done.**
2. Client archive core: per-chat keys, the grant record that delivers the archive key and join token, entry encryption, local schema. **Done.**
3. Send and receive integration: append before sending, catch-up from the archive, checkpoints, the "behind" warning. **Done**, with one change the maintainer chose: the archive entry does **not** come first. A message goes out by envelope exactly as before and its archive entry is queued separately, so an unreachable archive never delays or blocks a message.
4. Keyring: put and get, restore flow, "Restore from relay" in the app. **Done.**
5. Consent-based deletion and redaction (relay, engine, GUI). **Done.**
6. End-to-end tests: wipe a client and restore it, a hostile relay (withholds the tail, shows different heads), simultaneous senders. **Done.**

**Step 6 as built** (the final audit; tests only, no engine changes): the list was checked against what was already tested, and the gaps closed in `tests/test_group.cpp`.

- **A hostile member** (the realistic attack: a member holds the archive key). The test acts as a member whose app is off, using their real archive and chat keys read from their own history file, and adds entries to the archive: a message claiming to be from someone else but signed with their own key; a genuine message addressed to a different set of people; an entry not encrypted under the archive key at all; and a signed checkpoint contradicting the chain. Result: the forged and misdirected messages appear for nobody, the junk is skipped and the chain carries on, the contradicting checkpoint warns the other members, and a real message sent afterwards still reaches everyone.
- **A relay that alters an entry** nobody has read yet (one byte changed in the relay's database): members are warned when they next read it, and the message still reached them by envelope. **A relay that shows a different history of the same length** (the last entry swapped for another, with a valid chain): the member who read the original is warned (\"different end\").
- **Many writing at once:** three members write eight messages each in a burst; all 24 reach everyone, the three archives settle on one chain, no warnings. Then one member's device is wiped and restored: all 24 come back from the archive alone.
- **Restore after deletion:** a message everyone agreed to delete, and a chat deleted by agreement, do not come back; their neighbours do; no warnings.
- **A non-member forging a deletion request** is ignored. **Restoring with no saved keyring** says so plainly.
- **Mutation check:** four protections were removed in turn and the matching check failed for three: the signature check on entries read from the archive, the comparison of a member's checkpoint with the chain, and the chain's hash check. The fourth, the membership check inside the deletion-request handler, is not caught by this test because a non-member's request is already refused one layer earlier by the group's own membership check; the inner check is defence in depth.
- **Not covered end to end:** a relay too old to know about archives (the app just fails to make one and retries); a registration window that really expires (30 days) and the 7-day request expiry (the clock can't be moved); a no-show member who never joins an archive.

**M4 known limits, in one place:** restoring needs the keys folder and its passphrase (there is no other recovery); chats from before archives existed, and Private chats, can't be restored; messages archived before the deletion feature can't be named for deletion until their archive is read again; a relay can always delete what it holds, and a tombstone nobody agreed to is not flagged; there is no per-message delete action in the GUI yet; the GUI parts of M4 are only type-checked against a Qt stub here.

**Step 5 as built** (relay, `MessagingEngine`, `HistoryStore`, `ChatWidget`): deletion by agreement, kept **strict** as the maintainer chose: every member must accept; no majority.

- **Relay:** `ARCHIVE_DELETE` (0x51 reply `ARCHIVE_DELETE_OK`), from a session signed in to the archive. The order carries a scope (the whole chat, or 1 to 64 entries named by chain hash), a fresh 16-byte operation ID, an expiry, and one signature per registered key. Each member signs `archive_delete_signing_input` (relay ID, archive ID, scope, operation, expiry, entries in order) with their per-chat key, so a signature made for one order can't serve another. The relay refuses while registration is still open (a later joiner would have had no say), if any registered key hasn't signed or a signature is invalid, or the order has expired; an order naming an unknown entry changes nothing. Whole chat: the archive is removed. Entries: the content is replaced by a **tombstone that keeps its number and hash** (`redacted` flag on `archive_entries`, relay schema 6, `ALTER` for 4 and 5), and `ArchiveEntry` gained a tombstone flag on the wire (content xor tombstone). `archive::verify_chain` takes a tombstone's hash as given; the next entry's hash holds it in place.
- **Records:** `DeleteRequest` (8: scope, operation, expiry, entry hashes) and `DeleteAccept` (9: operation, key hash, the member's signature), version 2, outside the transcript. A request is appended to the archive and also sent to each member's envelope so they hear at once; an acceptance is appended and sent to the requester, who normally submits. Anyone holding every acceptance may submit; the relay decides if enough have signed, so a no-show who never joined can't block it (registered keys only).
- **Local state** (history schema 8, tables only): `deletions` (state: pending, accepted, declined, done, expired), `deletion_accepts`, `archive_messages` (message to entry number, filled while reading or appending, so a message can be named by its entry's hash), `archive_redacted`. A deleted message keeps its row, time, ID and entry hash but its sealed content is emptied (`Message::deleted`), so gap and chain logic carry on and the text isn't recoverable from the file. A whole-chat deletion erases the chat's messages and forgets its archive; `ensure_archives` does not make a new one.
- **Detecting that it happened:** the submitter applies it on success. Others who accepted notice in `check_deletions` (every `archive_sync_seconds`): a whole-chat order shows as a failed archive sign-in; an entries order shows as the entries coming back as tombstones with the expected hashes. Requests lapse after 7 days (checked there).
- **Engine API:** `request_chat_deletion`, `request_message_deletion`, `deletions()`, `accept_deletion`, `decline_deletion` (declining sends nothing; silence also means no). `ChatMessage` / `GroupMessage` have `deleted`.
- **GUI:** "Delete chat…" in the header, "Deletion requests (N)" in the top bar (Delete for everyone / Don't delete / Decide later, saying who asked, for what, how many have agreed and when it lapses), and a "(deleted by agreement)" line in place of a deleted message. **No per-message "delete this message" action in the GUI yet** (the engine supports it); messages need a selection control first.
- **Known limits:** messages archived before this version have no message-to-entry map, so they can't be named for redaction until their archive is read again (a restore does that); the 7-day expiry is enforced but untested; a relay can still delete entries by itself, and a tombstone nobody agreed to is not flagged (members are only warned about a dropped tail); a signature that doesn't verify makes the whole order fail, which can stall but not force a deletion.
- **Verified:** relay-level tests for missing, forged, reused-for-another-entry, expired and over-long orders, all-or-nothing redaction, the chain verifying across a tombstone, the whole-chat order and reusing the ID; and a three-person end-to-end test: with one decline nothing is deleted anywhere; with everyone agreeing the message is deleted on all three devices with its place kept and no warnings, the archive carrying on; the whole chat is deleted only when the last member accepts, and no one recreates it.

**Step 4 as built** (`client/keyring.{h,cpp}`, relay keyring slot, `MessagingEngine`, `ChatWidget`):

- **Relay slot:** `KEYRING_PUT` / `KEYRING_PUT_OK` / `KEYRING_GET` / `KEYRING_DATA` (0x4C to 0x4F), mailbox sign-in required, one opaque blob per mailbox in a new `keyrings` table (relay schema 5, removed with the mailbox). **Departures from the design:** the keyring travels in 48 KiB chunks, because one relay message is capped at about 68 KB; and the default limit is **4 MiB** (`--keyring-max-kib`), not 1 MiB, because each chat's private key is about 4 KB, so 1 MiB would hold only about 170 chats. An upload is assembled apart from the stored keyring and replaces it only when the last chunk arrives, so a dropped, out-of-order or inconsistent upload changes nothing. Chunk numbers are validated against each other (count from the total, index in range, exact data size).
- **Contents** (`keyring::Contents`, serialized deterministically, strictly parsed): each archive's address, relay ID, role, state, archive key, this device's per-chat key pair and join token (while granted); verified people; member tokens; introduced members (with bundles); issued-token labels, bindings and revocations; per-chat receipt settings. Not in it: messages (they come from archives), requests and invitations (lost on a wipe), and the keys folder itself. Sealed with AES-256-GCM under `derive_local_key("archive keyring")`, with the mailbox ID as associated data.
- **Keeping it current:** `maintain_keyring` (every `keyring_check_seconds`, default 60; first look one interval after start) builds the keyring and stores it only if its hash differs from what was last stored; `save_keyring` does it at once.
- **Restore** (`restore_from_relay`, also the GUI's "Restore history…"): fetch, open (a damaged keyring or the wrong keys gives a plain reason), restore the small tables and archive rows, then for each joined archive read the chain from entry 1 with every hash checked, rebuild the chat (a one-to-one chat from the contacts, since its ID is derived; a group from its creation record, the archive's first entry, verified against its creator, which `create_archive` now queues itself), and read the messages back: each is checked exactly as when it arrived (signature, membership, recipients hash), stored as read, with the user's own as sent (per-member delivery detail is not kept). Chats never archived, Private chats, and groups whose creator can't be verified are reported in `RestoreReport::notes`. Running it again adds nothing twice. The GUI says plainly that the same keys folder and passphrase are required.
- **Bug found on the way:** a pending group invitation counted every held record (tokens, the archive grant) as a message. `held_messages` now counts text messages only.
- **Verified:** the test wipes a member's history, restores from the relay, and checks groups, titles, members, messages from every member, own messages, the verified label on an introduced member, nothing marked unread, a second restore changing nothing, and that the restored device can send and archive again with its old keys; a damaged keyring is refused.
- **Building on a small machine:** the default CMake build also compiles the client core, and `messaging_engine.cpp` (about 2,000 lines) can take very long or a lot of memory on a small or single-core relay box. `cmake --build . --target pq-server` builds only the relay. This fixed the maintainer's stuck build.

**Step 3 as built** (`MessagingEngine`, history schema 7):

- **Automatic creation** (`ensure_archives`, every `archive_check_seconds`, first look one interval after start): for each group the user created, and for each one-to-one chat where the user's fingerprint is the smaller and the chat has at least one message (in either direction; the decision said "next send"), `create_archive` runs, retried every few seconds if the relay is down. A group's creation record is queued as the archive's first entry (it says who is in the group, which restore will need). Chats that already existed get an archive too; their older history is not backfilled.
- **Sending:** `send_text` / `send_group_text` queue an `OUTBOX_KIND_ARCHIVE` item (the chat's ID in hex, one signed record) next to the envelopes, only if the chat already has an archive. `flush_archive_item` appends it with `archive_append` (catching up and retrying as before), waits if the device hasn't joined yet, drops it if joining failed, and backs off if the relay can't be reached.
- **Receiving from the archive** (`handle_archived_records`): records found while syncing get the same signature, membership and recipients checks as ones from an envelope, and nothing already held is added twice, so a message that never came by envelope turns up from the archive. `sync_archives` catches up on each joined archive every `archive_sync_seconds`, and straight away when a message shows a gap (`archive_sync_now_`).
- **Checkpoints** (`RecordType::Checkpoint`, 7, version 2 only, archive only): after `archive_checkpoint_every` entries other than checkpoints (default 50) since the last one, or some activity and a day, a member adds a signed "I have seen entry n, whose hash is h" to the archive. The history store keeps the chain hash of every entry this device has checked (`archive_chain`), so `process_checkpoint` can compare a member's checkpoint with it.
- **Warnings** (`ArchiveStatus::warning`, `warn_archive`): set once, and notified, when the relay's copy doesn't match what this device holds (entries altered or out of order; the reported end differs from what the entries add up to, which is what a relay dropping the end of the log looks like; a member's checkpoint contradicts our chain). They never clear themselves: someone has to look. A damaged archive never stops messages, which still flow by envelope.
- **History schema 7:** four new columns on `archives` (when we last added a checkpoint, activity since, the highest checkpoint seen, the warning) and the `archive_chain` table; a version 6 database gets the columns by `ALTER TABLE` (tested on a real version 6 fixture).
- **Not yet:** the keyring and restore (step 4), deletion and redaction (5), any GUI for archive status or warnings (a later GUI slice; the engine reports it through `archive_status`).

**Step 2 as built** (`client/archive.{h,cpp}`, `HistoryStore`, `MessagingEngine`):

- **Entries** (`archive::seal_entry` / `open_entry`): `nonce(12) || AES-256-GCM(archive key, one signed record)` with the archive ID and entry number as associated data. **Departure from the design:** the nonce is random and stored with the entry, not the entry number. A refused (stale) append still shows the relay its ciphertext, so two members racing for the same number would encrypt different records under the same key and nonce, which leaks both. `archive::verify_chain` checks consecutive numbers and each hash from a given head; the chain hashing matches the relay's byte for byte.
- **Grant record** (`RecordType::ArchiveGrant`, 6, version 2 only, outside the transcript like receipts and forwards): relay address, relay ID, the 32-byte archive key and that member's 32-byte join token, each member's in their own sealed envelope. Accepted only from the person whose job it is (a group's creator; in a 1:1 chat the smaller fingerprint) and only for a chat we know; a second grant for a chat that already has an archive is ignored (a replay can't swap the key). Grants arriving before a group invitation is answered are held with it and replayed on accept.
- **Local state** (history schema 6, table `archives`): relay address and ID, role, state (granted, joined, failed), the archive key, this device's per-chat key pair, the join token until used, the checked head, and a failure note. The key, private key and token are encrypted like messages; the head only moves forward.
- **Engine API:** `direct_conversation_id`, `archive_status`, `create_archive` (the maker only; creates the archive on this app's relay with one token hash per member including themselves, joins, then queues each other member's grant as an ordinary outbox item), `archive_sync` (fetches from the checked head, verifies the chain, decrypts, and fails if the relay's reported end differs from what its entries add up to, which catches a withheld tail or a lying head), `archive_append` (catches up, seals for the next number, appends; if someone got in first it catches up on theirs, hands them back in `others`, and goes again; checks the relay's answer matches the entry it made). `pump()` joins any granted archive each time round (a refusal is final, a relay that is down is retried).
- **Not yet wired in:** nothing calls `create_archive` or `archive_append` during normal use. Step 3 does that: create at group creation and on a 1:1 chat's next send, append before fanning out, catch up on a gap, checkpoints.

**Step 1 as built** (`RelayStore`, `RelayService`, `RelayClient`; protocol in `relay_protocol.h`, messages 0x40 to 0x4B):

- **Create** (mailbox sign-in required): archive ID (the conversation ID) and one **join token hash per member** (1 to 16). The creator makes the tokens, so the relay only ever holds hashes, and gives each member theirs.
- **Join** (no mailbox): a member presents the token and registers a fresh per-chat ML-DSA-65 public key, proving possession by signing over relay ID, archive ID, key and token hash. The token is spent. Registration closes when every member has joined or after 30 days. Wrong token and unknown archive give the same answer, so archive IDs can't be probed.
- **Sign in**: one chat per connection, signing the connection's challenge with a registered key (same one-attempt rule as a mailbox sign-in).
- **Append**: the sender names the head it extends (entry number and hash; the *genesis hash* is the head of an empty archive). The relay accepts only if that is still the head (compare-and-swap) and **computes the new hash itself**: SHA-256 over archive ID, entry number, previous hash and ciphertext. If the head moved it answers `ARCHIVE_STALE` with the current head and the sender fetches what it missed and re-signs on top. (Simplification of the design, which has the relay return the new entries: entries can be 64 KiB each, so they come from a fetch instead.)
- **Fetch**: entries from a number onwards, up to 256, as separate messages then the head.
- **Limits**: entry 64 KiB; `--archive-quota-mib` per archive (default 512); `--max-archives` per relay (default 1000). Archives nobody joined before the registration window closed are swept away. Relay database schema 4 (new tables only).
- **Not yet on the relay:** the keyring slot and deletion/redaction (step 4 and 5), tombstones, per-archive checkpoints (those are chain entries, so the relay needs nothing).
- Verified: chain hashes match an independent calculation in the tests; a stale append is refused; simultaneous appenders get one winner and one retry; outsiders and keys from another archive can't sign in; quota, restart, and that no table has a column linking an archive to a mailbox.

## Member-issued relay invites

Anyone with a mailbox on a relay can make single-use invites for friends; the relay records who vouched for whom. Chosen over open registration (an invite handed to anyone who asks is no invite; per-address rate limits are easy to dodge and punish shared addresses) and over operator approval (needs the operator online).

- **Protocol:** `RELAY_INVITE_CREATE` (0x32, owner-only, empty payload) and `RELAY_INVITE_OK` (0x33, the 16-byte invite); `RELAY_INVITE_LIST` (0x34) answered by `RELAY_INVITE_LIST_OK` (0x35, `relay::InviteStatus`: the relay's two limits, the member's unused invites as hash and expiry, and the people who joined through them as mailbox ID and time); `RELAY_INVITE_CANCEL` (0x36, an invite hash) answered by `RELAY_INVITE_CANCEL_OK` (0x37). Additive: an older relay answers "Unexpected message" and closes, so the app shows an error until the relay is updated. The relay stores only invite hashes, so an unused invite is identified by hash and the app cannot say who an invite was for; only the member knows that.
- **Relay database, schema version 3:** `invites.issued_by` and `mailboxes.invited_by` (NULL for operator invites). A version 1 or 2 database upgrades in place on first start (`ALTER TABLE`; tested against fixtures built exactly as the old versions made them).
- **Limits** (`RelayLimits`, flags `--member-invites`, `--member-invites-total`): unused invites at once per member (default 3; 0 turns the feature off) and people ever invited per member (default 10), counted from the database, so a restart doesn't reset them. A member also has a rate limit of 10 requests a minute. The relay-wide caps (1,000 mailboxes, registration rate per address) still apply.
- **Operator tools:** `--list-mailboxes`, `--remove-mailbox ID [--with-invitees]` (see README). Removing a mailbox deletes its tokens, queued envelopes and the unused invites it made; mailboxes it invited stay unless `--with-invitees` (a `*` in the listing marks one whose voucher is gone).
- **Client:** `RelayClient::create_invite` / `list_invites` / `cancel_invite`; `MessagingEngine::create_relay_invite` (builds a `pqft-relay://` string from the member's own relay address, pinned relay ID and the new code), `relay_invite_status` and `cancel_relay_invite`; and a "Relay invites…" dialog in `ChatWidget`: the limits, the unused invites with expiry, when people joined, New invite (shows the string with a Copy button and a reminder that the member is vouching and that the address may need changing for a friend who reaches the relay another way) and Cancel selected.
- **Decided, not built:** (a) no push notification when an invite is used: the relay can only push to a connected owner, so it would be missed while the app is closed; the "Relay invites…" dialog shows who joined and when, which covers the need. (b) no operator view inside the app: the operator is not a mailbox and cannot authenticate to one; `--list-mailboxes` and `--remove-mailbox` are the operator's tools. **Planned for M8 (hardening):** encrypted relay connections. Invites and send tokens cross the network unencrypted today, like all relay traffic (the README says so); the relay is meant to sit on a trusted network such as a WireGuard tunnel.

## M3: decisions and build order

Settled with the maintainer; they are also in the design document's build log, which wins on any disagreement. A group is at most 16 people including you; membership is fixed at creation.

| # | Decision |
|---|---|
| 1 | The creation record holds the conversation ID, creator, member **fingerprints only**, mode, timer, an optional group title and an optional link to a previous conversation. No bundles (a real bundle is 6,597 bytes, so 16 would be about 105 KB). |
| 2 | The creator sends the other members' self-signed bundles in a new `introduced` list inside the envelope (envelope inner version 2; about 8 bundles fit in one 64 KiB envelope, so two envelopes for 15 others). The creator's signed record names which fingerprints are allowed. |
| 3 | Each member makes a token for each other member, and the grant is forwarded **through the creator**, sealed so the creator can't read it. No grant is needed where two members already hold working tokens as contacts. A new group shows "setting up" until the grants arrive. |
| 4 | `seen` in a record becomes a **list** of the latest hash received from each other member (at most 15), record version 2; version 1 records still parse. |
| 5 | Trust labels: a new `verified` flag (the user compared fingerprints), introduced members kept apart from contacts with who introduced them. Labels: Verified by you / Contact / Introduced by X. ("Key changed" from the first design doesn't apply: identity is the signing-key fingerprint, so a different signing key is a different person; encryption-key changes already produce a notice.) |
| 6 | Receipts go only to the message's author; the sender sees per-member status. |
| 7 | Relay default `max_tokens_per_mailbox` goes from 256 to 1024 (the only relay-side change). |
| 8 | Local database schema 1 to 2 (done): conversations gain kind, state, title, creator, mode, timer and previous-conversation link; members and per-member delivery get their own tables. |

Build order, with what is done:

1. Settle decisions and record them. **Done.**
2. Database migration and per-member delivery, one-to-one behaviour unchanged. **Done** (`HistoryStore`: `create_group`, `conversation`, `set_conversation_state`, `raise_delivery`, `deliveries`; the engine's one-to-one path now uses `raise_delivery`).
3. Creation record, record version 2 and envelope version 2, each with tamper tests on every field. **Done.** `message_record.h`: `RecordType::Conversation` (4), `ConversationInfo` with `conversation_payload`, `parse_conversation_payload` and `conversation_from_record` (checks the creator is a member and the recipients hash matches the list); `Record::seen` is now a list (at most 15, distinct), version 1 records are still read; titles must be strict UTF-8 without control or direction-override characters. `envelope.h`: `Inner::introduced` (declared last, with an initializer, so `{bundle, records}` built positionally keeps its meaning), `encode_inner` and `decode_inner` exposed for tests; inner version 1 is still read. A real bundle is 6,597 bytes: at least 8 fit in one envelope beside a creation record (measured), 15 do not.
4. Engine: create, fan-out, group invite as a request, accept and decline, membership checks, group receipts. **Done.** Public API in `MessagingEngine`: `create_group`, `groups`, `group_messages`, `group_delivery`, `send_group_text`, `mark_group_read`, `set_group_receipts` / `group_receipts_enabled`, `group_invites`, `accept_group_invite`, `decline_group_invite`. How it works: an invitation from a contact waits in `HistoryStore` group invitations until answered, with messages that arrive meanwhile held with it (at most 200) and replayed on accept. An invitation from a non-contact arrives as a message request first (its records, then the introduced bundles, are stored in the request); accepting that person re-handles it as an invitation from a contact. The creator introduces the other members' bundles in `Inner::introduced`, at most 6 per envelope; longer lists are split across envelopes that each repeat the creation record, and a repeat of the identical record adds its bundles but changes nothing else. `Peer` / `resolve_peer` finds someone to verify or write to: a contact, else an introduced member (verifiable, but with no send token until step 5, so `can_send` is false and a group with such members shows `ready == false`). Group records are accepted only from members and only if their recipients hash matches the member list; a creation record for an existing group changes nothing. A receipt goes only to the message's author. The outbox holds one item per recipient; an item's `records` are signed records plus, for invitations, identity bundles to introduce (told apart by whether `parse_record` accepts them).
5. Token grants and forwarding through the creator; raise the relay token cap. **Done.** When a member accepts a group, `queue_group_grants` queues a job (outbox kind 2) for the creator: for each other member except the creator, unless they are a contact who has already used a token of ours. On the relay thread `build_grant_forwards` makes a fresh send token per member (registered with our relay, recorded as issued and bound to that member, so passing it on is reported like a passed-on card), seals a TokenGrant record inside an envelope only that member can open, and wraps it in a signed `Forward` record (type 5) to the creator, four per envelope. The creator (`handle_group_record`) checks the sender and the target are members of a group it created and deposits the sealed envelope unread (outbox kind 3, `OUTBOX_KIND_RELAY`). The member who gets it stores the token for that group and that member only (`HistoryStore::member_token`, encrypted); `resolve_peer(fp, conversation_id)` uses it when there is no other way to write to them, so the group becomes ready. Grants that arrive before the invitation is answered are held with it. A forwarded grant arrives through the creator's token, so it is not counted as use of a card. Someone known only from a group (not a contact) gets no first-message introduction. The relay's default token limit is 1024. If the creator is offline, members who aren't contacts stay "not ready" until it returns (the relay holds the envelopes).
6. Trust labels. **Done.** `HistoryStore` keeps a table of verified people (`set_verified`, `is_verified`): it is about the person, so it holds whether they are a contact or only known from a group, and carries over if one becomes the other. `MessagingEngine::GroupMember` now has `trust` (`Unknown`, `Introduced`, `Contact`, `Verified`), `introduced_by` (a name) and a ready-made `label` ("Verified by you", "Contact", "Introduced by Alice", "Unknown"); `ChatSummary` has `verified`. `set_verified(fp, bool)` works for contacts and introduced members (false for strangers). `accept_request` marks the person verified, because the app has the user check their fingerprint first. A newer bundle from an introduced member with a different encryption key raises the same "is using a new encryption key" notice as for contacts. (The GUI side of this, including marking a contact verified after the add-contact fingerprint dialog, is slice 4 of step 7.)
7. GUI (last; it can't be built in the assistant's sandbox, so GUI changes are only type-checked against a hand-written Qt stub). **In progress, in slices.** Slice 1 done: `ChatWidget` has a "Groups" list under the contacts (hidden until a group exists) showing each group's title, unread count and "(setting up)" while some member can't be written to; the tooltip lists members with their trust labels (escaped, since titles and names come from other people); selecting a group shows its messages read-only (sender names, delivery words), marks them read, and the receipt checkboxes work per group; the header lists members and who we can't write to yet. Selecting a contact and a group is mutually exclusive. Slice 2 done: a "New group…" button (name plus tick-boxes for contacts you can message, up to 15; the engine validates) and a "Group invitations (N)" button that walks through pending invitations (Join, Decline, Decide later) showing the creator, the others with their trust labels and a note about "Introduced" people, and how many messages arrived while waiting; creating or joining selects the group. Plain-text sending to a group works too (queued per member, whether or not everyone is reachable yet), in `send_current`. An invitation from someone who isn't a contact still arrives as a message request first. Slice 3 done: your messages in a group show how far they have got in true terms ("sent to 2 of 3", "sent to everyone, delivered to 1 of 3", "delivered to everyone", "read by everyone"; computed for the newest 50 outgoing messages not yet read by all), and clicking one opens a plain-text dialog with each member's own state and why it may be stuck (can't write to them yet / sent but not confirmed, e.g. receipts off or the relay still holding it). It relies on `QListWidget::itemClicked` firing with the list in NoSelection mode, which is not verified. Slice 4 done: the group header lists members with their trust labels; a header button reads "Members…" for a group (a dialog listing everyone with label, who made the group and who can't be written to yet, with a Fingerprint… button) and "Verify…" for a contact (their fingerprint, with "It matches: mark as verified" or "Remove verified mark"); a contact's header shows "(verified by you)" or "(not verified)"; and `main_window.cpp` `finish_add_contact` calls `ChatWidget::mark_verified(fp)` after the user answers "Yes" to "Does the fingerprint match?". Message-request accept already verifies (engine).
8. Three-user end-to-end tests: an offline member, and hostile cases (a non-member sender, a wrong recipients hash, a replayed creation record, a creator who lies about the members). **Done** in `tests/test_group.cpp` (a real relay and up to 18 real engines). Audited against the list; added what was missing: the creator cannot open the tokens it passes on (read raw from the target's mailbox: nothing opens with the creator's key, everything opens with the target's, and one item is a 32-byte token signed by the sender for that group); only a member may ask the creator to pass something on, for another member, in a group the creator made (non-member target, self-target and a non-creator obeying a Forward each deposit nothing; a valid request deposits one envelope); and a flood of 55 invitations keeps 50. Each guard was removed in turn and the matching check failed.

Notes for whoever continues: `HistoryStore::raise_delivery` computes a message's overall status as the **lowest** across the conversation's members, so a message never shows as sent or delivered until everyone has it; a receipt from a non-member is ignored. `create_group` on an existing ID returns the existing group unchanged, so a replayed creation record can't alter a group.
